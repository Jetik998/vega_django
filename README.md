# Документация проекта: Vega Django (Система учета ремонта техники)

Веб-приложение для сервисных центров и мастерских, позволяющее вести приемку техники, отслеживать этапы ремонта, формировать историю смены статусов и фильтровать заказы по различным критериям.

---

## 1. Архитектура и стек технологий

### Стек

- **Backend:** Python 3.12, Django 5.x
- **Frontend:** Django Templates, Bootstrap 5 (CDN)
- **База данных:** SQLite (хранится в томе на хосте, сохраняет данные при перезапусках)
- **Web-сервер / Reverse Proxy:** Nginx (Alpine) с поддержкой SSL/TLS
- **Контейнеризация:** Docker & Docker Compose

### Схема взаимодействия компонентов

```text
Клиент (Браузер)
       │
       ▼  (Порты 80 / 443 SSL)
┌─────────────────────────────────────────────────────────┐
│ Nginx (Контейнер vega_repair_nginx)                     │
│  - Редирект 80 (HTTP) -> 443 (HTTPS)                    │
│  - Терминация SSL (сертификаты из /etc/nginx/certs)     │
│  - Проксирование на внутреннюю сеть Docker              │
└───────────────────────────┬─────────────────────────────┘
                            │ (http://web:8000)
                            ▼
┌─────────────────────────────────────────────────────────┐
│ Django App (Контейнер vega_repair_web)                  │
│  - Обработка бизнес-логики и маршрутов                  │
│  - Авто-история статусов                                 │
│  - Генератор 8-значных штрихкодов                        │
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
                     [ db.sqlite3 ] (Том на хосте)
```

## 3. Описание модулей и логики работы

### 3.1. База данных (`repairs/models.py`)

#### `generate_barcode()`

- Автоматически генерирует случайный 8-значный цифровой идентификатор заказа.
- Проверяет базу на коллизии: если номер уже занят, повторяет генерацию до получения уникального ID.

#### Модель `Repair` (Заказ на ремонт)

Хранит основную информацию по заказу:

- `id` — 8-значный штрихкод (Primary Key).
- `client_name`, `client_phone`, `device_model` — обязательные поля данных клиента и устройства.
- `issue_description` — текст заявленной неисправности.
- `status` — текущий этап: `Принято`, `В работе`, `Готово`, `Выдано`.
- `completed_works`, `cost` — выполненные работы и стоимость.
- `accepted_at`, `issued_at` — дата приема и автоматическая дата выдачи.

**Логика в методе `save()`:**

- Если статус переводится в `Выдано`, а дата выдачи еще не проставлена, Django автоматически проставляет текущую дату и время (`timezone.now()`).
- При каждом сохранении заказа автоматически создается запись в таблице `StatusHistory`.

#### Модель `StatusHistory` (История статусов)

- Реализует аудит заказов.
- Связана с `Repair` через `ForeignKey` (`related_name='history'`).
- При удалении заказа каскадно удаляет всю историю.

---

### 3.2. Представления (`repairs/views.py`)

#### `dashboard(request)` — главная страница

**GET-запрос — фильтрация и поиск:**

- Поиск по штрихкоду/ID (`q`).
- Поиск по части имени клиента или модели устройства (`icontains`).
- Множественный фильтр по статусам (чекбоксы).
- Фильтр по временным отрезкам:
  - `today` — за сегодня;
  - `week` — последние 7 дней;
  - `month` — последние 30 дней.

**POST-запрос — создание заказа:**

- Валидирует и создает новую запись в БД.
- Принимает как автоматически сгенерированный ID, так и введенный вручную со сканера штрихкода.

#### `repair_detail(request, pk)` — карточка заказа

**GET-запрос:**

- Отображает полную информацию по заказу.
- Показывает форму изменения статуса.
- Отображает таблицу всех предыдущих изменений из `StatusHistory`.

**POST-запрос:**

- Обновляет текущий статус.
- Обновляет описание выполненных работ.
- Обновляет итоговую стоимость.
- Вызывает переопределенный метод `save()` модели, который обеспечивает сохранение истории изменений.

---

### 3.3. Шаблоны и интерфейс (`templates/repairs/`)

#### `dashboard.html`

Главная страница приложения включает:

- левую колонку с формой быстрой приемки техники в ремонт;
- верхнюю панель с фильтрами по клиенту, технике, статусам и периодам;
- таблицу заказов.

Строки таблицы динамически подсвечиваются в зависимости от текущего статуса:

| Статус | Цвет |
|---|---|
| Принято | Белый (`#ffffff`) |
| В работе | Розовый / красный (`#ffcdd2`) |
| Готово | Светло-зеленый (`#c8e6c9`) |
| Выдано | Нейтральный серый (`#e0e0e0`) |

#### `detail.html`

Карточка конкретного заказа включает:

- данные клиента;
- данные устройства;
- описание неисправности;
- текущий статус;
- описание выполненных работ;
- итоговую стоимость;
- форму редактирования;
- таблицу с хронологией смены статусов и работ.

## 4. Контейнеризация и инфраструктура (Nginx + SSL)

### 4.1. `nginx.conf`

#### HTTP — порт 80

Выполняет безусловный `301`-редирект всего входящего HTTP-трафика на HTTPS:

```nginx
https://$host$request_uri
```

#### HTTPS — порт 443

Nginx:

- подключает SSL-сертификаты `fullchain.pem` и `privkey.pem`;
- включает протоколы TLS 1.2 и TLS 1.3;
- проксирует запросы на внутренний контейнер Django `http://web:8000`;
- сохраняет исходные заголовки клиента:
  - `X-Real-IP`;
  - `X-Forwarded-For`;
  - `X-Forwarded-Proto`.

Таким образом, внешний клиент работает с HTTPS, а внутри Docker-сети Nginx передает запросы Django-приложению.

---

### 4.2. `docker-compose.yml`

#### Сервис `web`

- Собирается из `Dockerfile`.
- Использует базовый образ `python:3.12-slim`.
- Запускает Django-приложение.
- Изолирован во внутренней сети Docker.
- Монтирует текущую директорию в `/app`.
- Благодаря монтированию директории база `db.sqlite3` сохраняется на хосте и не теряется при пересоздании контейнера.

#### Сервис `nginx`

- Использует образ `nginx:alpine`.
- Пробрасывает порты:
  - `80:80`;
  - `443:443`.
- Монтирует конфигурацию Nginx.
- Монтирует директорию с SSL-сертификатами хоста:

```text
/root/cert/ip:/etc/nginx/certs:ro
```

- Использует `depends_on` для запуска после контейнера приложения:

```yaml
depends_on:
  - web
```


```bash
docker compose down && docker compose up -d --build
```

Эта команда:

1. останавливает текущие контейнеры;
2. удаляет контейнеры;
3. пересобирает Docker-образы;
4. запускает проект в фоновом режиме.

Ключ `-f` позволяет следить за логами в реальном времени.

Для выхода из просмотра логов используется:

```bash
docker compose logs -f nginx
```

## 6. Основной рабочий процесс

Типовой цикл работы с заказом выглядит следующим образом:

```text
Приемка техники
      │
      ▼
Создание Repair
      │
      ▼
Статус: "Принято"
      │
      ▼
Диагностика / ремонт
      │
      ▼
Статус: "В работе"
      │
      ▼
Завершение работ
      │
      ▼
Статус: "Готово"
      │
      ▼
Выдача клиенту
      │
      ▼
Статус: "Выдано"
      │
      ▼
Автоматическая фиксация issued_at
```

Каждое сохранение заказа сопровождается созданием записи в `StatusHistory`, благодаря чему сохраняется история изменений заказа.

## 8. Важные особенности проекта

- Заказы имеют 8-значный цифровой идентификатор, используемый как штрихкод.
- Идентификатор может быть сгенерирован автоматически либо передан вручную со сканера.
- Для предотвращения коллизий при автоматической генерации ID выполняется проверка существующих записей.
- История статусов сохраняется отдельно в `StatusHistory`.
- При переводе заказа в статус `Выдано` автоматически фиксируется дата и время выдачи.
- SQLite хранится вне жизненного цикла контейнера благодаря монтированию директории проекта.
- Nginx является внешней точкой входа и отвечает за HTTPS.
- Django работает во внутренней Docker-сети и принимает запросы от Nginx.
- Для управления проектом используются стандартные команды Docker Compose и Django `manage.py`.

## 9. Быстрый запуск и обслуживание

Основные команды:

```bash
# Пересборка и запуск
docker compose down && docker compose up -d --build

# Логи Django
docker compose logs -f web

# Логи Nginx
docker compose logs -f nginx

# Миграции
docker compose exec web python manage.py migrate

# Создание администратора
docker compose exec web python manage.py createsuperuser
```

Проект представляет собой монолитное Django-приложение, работающее в Docker-контейнере за Nginx reverse proxy. Данные заказов и история их изменений хранятся в SQLite, расположенной в директории проекта на хосте.
